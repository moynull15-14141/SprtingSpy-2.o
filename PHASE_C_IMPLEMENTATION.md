## 1. Rich Text Editor

- **Editor:** TipTap 3.31 (StarterKit + Image + Table), in `src/components/admin/editor/RichTextEditor.tsx`. It lives only in the CMS bundle and loads lazily through `next/dynamic`. A test confirms none of the public page chunks contain TipTap or ProseMirror code.
- **Supported content:**
  - paragraphs and semantic **H2/H3/H4** headings (H1 stays the article title)
  - bold, italic
  - links with a link type (Spec §13): *editorial*, *nofollow*, *sponsored* or *UGC*, plus an optional new tab. New-tab links always get `noopener noreferrer`. Only `https://`, `mailto:` and site paths are accepted.
  - bulleted and numbered lists, blockquote, horizontal rule
  - **tables**: insert, add/remove rows and columns, edit cells
  - **images chosen from the Media Library**, stored as a `mediaId` reference
- **Warnings:** heading-structure warnings (skipped levels, empty headings) and live validation errors appear under the editor.
- **Embeds:** not implemented. Spec v1.1 doesn't list embeds; this is noted in Known Limitations.
- **Storage format:** a JSON document in the new `Article.body` column. `src/lib/richText.ts` defines one strict allow-list, used both by the server validator (on every create/update) and by the renderer:
  - no HTML strings are ever stored
  - unknown nodes, marks and attributes, unsafe links and non-library images are rejected with a clear message, never silently dropped
  - size, depth and node-count limits apply
- **Derived fields:** the server re-derives `content` (plain-text projection, used for search and reading time) and the image URLs, which come from the library, never from the client.
- **Rendering:** `RichText.tsx` is a server component that renders React elements. There is no `dangerouslySetInnerHTML`.
  - tables sit in their own scroll container, so there's no page overflow on mobile (tested at 390 px)
  - images render as responsive `<picture>` elements
  - the in-article ad slot stays after the 2nd paragraph
- **Legacy bodies:** pre-Phase-C bodies (the plain-text `### `, `- `, `**bold**` format) render through the same renderer via `legacyToDoc()`. Their stored data is unchanged; each article converts to the rich format the first time an editor saves it. A side effect: `**bold**` used to show as literal asterisks, and now renders as bold.

## 2. Preview

- **Route:** `/admin/preview/<articleId>/`, a Next.js server page. It renders the **same `ArticlePage` template** as the public page, with a "PREVIEW — status: …" banner and no article JSON-LD.
- **Access:** the session cookie is resolved on the server with the same shared rules as the API (`server/sessionLookup.ts`):
  - allowed: active Admin, Editor or Author accounts (Authors only for their own articles)
  - everyone else gets a **real 404**, so the existence of a draft is never revealed
- **Page properties:** `noindex, nofollow`, uncached (dynamic), and under `/admin`, which robots.txt disallows.
- **Never publishes:**
  - viewing a preview doesn't change status (tested)
  - in the editor, "Save draft & preview" saves unpublished articles with their current status
  - for live articles the button becomes "Preview saved version", which doesn't save
  - new articles now start as **Draft** (previously Published)
- **No draft leaks:** drafts are verified absent from public pages, the sitemap, search, listings and JSON-LD.

## 3. Media

- **Architecture:**
  `CMS → /api/media (server/media/routes.ts) → media service (service.ts) → MediaStorageProvider (storage.ts) → local disk`
  React components never touch file paths.
- **Providers:** `MEDIA_STORAGE_PROVIDER=local` is implemented, writing to `MEDIA_LOCAL_DIR` (default `storage/media`, gitignored, served at `/media`). The S3/R2 providers plug into the same interface. Requesting one now **fails at startup** instead of silently storing locally, because no bucket credentials exist.
- **Upload validation (all server-side):**
  - staff role and CSRF token required
  - multer memory upload: one file, 10 MB max
  - magic bytes, the file extension, the declared MIME type and the format sharp actually decodes must all agree
  - accepted: JPEG, PNG, WebP, AVIF
  - rejected (tested): SVG, HTML disguised as PNG, mismatches, animated images, anything under 16 px or over 12,000 px, over 50 MP or over 10 MB, and empty files
- **Storage keys and filenames:** keys are generated by the server (`YYYY/MM/<uuid>/…`) and validated again inside the provider, with a traversal guard. Files are written with `wx`, so they're never overwritten. The original filename is kept only as sanitized display text.
- **Processing (sharp):**
  - EXIF orientation is applied and **all metadata is stripped** (a GPS/EXIF marker was verified gone)
  - original: same format, long edge capped at 2560 px
  - variants: **400 / 800 / 1600 px plus the original width, in AVIF and WebP**, never upscaled (at most 9 files per image)
- **Delivery:**
  - `<picture>` with AVIF and WebP `srcset` plus `sizes`, and a JPEG/PNG fallback `<img>`
  - real `width`/`height` (no layout shift), lazy loading below the fold, eager + `fetchpriority=high` for the featured image
  - files are served with explicit content types (a bug fix: Express served `.avif` as octet-stream), `Cache-Control: immutable, 1 year`, and `nosniff`
  - Chrome was verified to actually load AVIF/WebP

## 5. Media relations & usage

- **Featured image:** `Article.featuredMediaId → MediaItem`, with `onDelete: Restrict`. `featuredImage` (the URL) is kept in sync as the fallback.
- **Body images:** the new `ArticleMedia(articleId, mediaId)` table, rebuilt on every save.
- **Usage history:**
  - article featured images and body images come from the relations
  - sport, event and edition images are matched by URL (those still store URLs)
  - the CMS shows "Used in …" per image and filters **unused** media
- **Deleting:**
  - media that is in use can't be deleted (409), and only Admins may delete
  - deleting removes the record and its stored files
  - nothing is ever deleted automatically

## 7. Redirects

- **Automatic article-URL redirects:** when a **published** article's URL changes (slug, sport, event or edition), the old URL gets a **301 to the new URL, in one hop**, recorded as `origin: article-slug`.
  - moving A→B→C gives A→C and B→C (no chains)
  - moving back to A retires A's rule instead of creating a loop
  - an old rule that would shadow a newly published article's URL is deactivated and kept for history
  - URL collisions with another article are rejected (409). The old update route had no such check.
  - drafts create no redirects
- **Safety, one module (`server/redirects.ts`) for manual and automatic rules:**
  - `sourceUrl` is **UNIQUE** in the database; sources are normalized without the trailing slash, so `/x` and `/x/` count as duplicates
  - self-redirects and loops are rejected
  - a new rule points at the final destination, and existing rules pointing at its source are re-targeted to it
  - saves that change nothing don't touch the row
- **Manual fields:** source, target, 301/302, active, **notes**, `origin`, `createdAt`, **`updatedAt`**. Admin only, CSRF-protected.
- **Bulk CSV import:** not implemented. It belongs to the migration phase (Spec §31) and isn't part of the redirect manager's current workflow.

## 8. Settings

- **Registry:** `server/settingsRegistry.ts` (an allow-list with a validator per key) plus the `SiteSetting` key/value table.
- **Access:** **Admin only** for reading and writing. Anonymous users get 401, Editors 403, CSRF is enforced, and changes are audited. There's an Admin-only "Settings" tab in the CMS.
- **Keys by group:**
  - **Site identity:** `siteName`, `siteDescription`
  - **SEO & social defaults:** `defaultOgImage`, `twitterHandle`
  - **Search engine verification:** `googleSiteVerification`, `bingSiteVerification`
  - **Analytics & advertising IDs:** `ga4MeasurementId`, `adsensePublisherId`
- **Public exposure:** only the two verification tokens are rendered publicly, as `<meta>` tags in the root layout. The GA4 and AdSense IDs are stored but never sent to public pages (tested). Wiring them up belongs to later phases.

## 11. Security

- **Upload:** staff and CSRF required. Type is verified by content, and size, dimension and pixel limits apply. SVG, HTML and scripts are rejected. Keys are server-generated, filenames are never trusted, and files are never overwritten. EXIF and GPS are stripped. Files are served with fixed image content types and `nosniff`.
- **Media API:** metadata editing is Admin/Editor; deleting is Admin-only and blocked while in use; there's no public listing.
- **Preview:** a server-side session check using the API's rules; the Author ownership rule applies; everyone else gets a 404; noindex/nofollow.
- **Settings:** Admin only; allow-listed and validated; only the verification tokens are public.
- **Rich content:** strict server allow-list; no stored HTML; no raw HTML rendering; unsafe links rejected.
- **RBAC/CSRF/sessions:** unchanged. Session resolution is now shared between Express and Next.js. All Phase 4, Production and Phase A security groups pass.

## 13. Known limitations

- **S3/R2 storage:** not implemented. The interface is ready, and the setting fails fast. When a CDN or bucket domain is used (`MEDIA_PUBLIC_BASE_URL`), the CSP `img-src` needs that domain added. CMS thumbnails currently assume `/media`.
- **Public media URLs:** stored files are public by unguessable URL. That includes images uploaded for drafts; access control applies to the library, not to the image bytes.
- **Processing time:** processing runs inside the upload request. A large image takes a few seconds for AVIF encoding. There's no background queue.
- **Embeds:** not implemented, since the spec doesn't require them.
- **Previewing live articles:** it shows the last saved version. There's no "preview unsaved changes" for published articles.
- **Behavior change:** new articles default to **Draft**.
- **Bulk CSV redirect import:** deferred to the migration phase.
- **Settings:** only the verification tags are active; the analytics, advertising and social values are stored for later phases.
- **Sport/event/edition images:** they still store URLs, not media relations. Usage for those is detected by URL match.
- **Legacy metadata:** the 5 legacy items keep their old `dimensions` strings ("1920x1080") next to the real `width`/`height` (1200 px). Their `copyrightReview` is `pending`; no clearance is claimed.
- **Legacy bodies:** they stay in the plain-text format until an editor saves them.
- **Test stability:** after the focus fix, Phase C passed 10 of 11 consecutive runs. One run early in that sequence failed without a captured message and didn't reproduce in the next 10 runs.
- **Sitemap:** it still lists every author profile. This is Phase D sitemap work.
